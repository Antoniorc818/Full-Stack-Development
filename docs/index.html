Professional Self-Assessment

More than any one course alone, finishing the Computer Science program at SNHU and creating this ePortfolio in particular altered my perspective on the work. When I first started, I mostly thought of computer science as developing functional code. Particularly in the past year, the program has encouraged me to think about writing code that is understandable to those who did not write it, works for someone, and endures in real-world scenarios. In reality, everything following revolves around that change.

Collaborating in a Team Environment

Since I've completed individual projects for the majority of my schooling, the best illustration of teamwork is in IT 204, where my group was tasked with researching IBM Db2 as the DBMS for a database proposal for Birchwood Lane Schools, a fake client. The actual skills I practiced were different from the work itself, which involved database design and an ER model with entities like Student, Instructor, Course, Enrollment, and Guardian. These included reconciling a schema decision with teammates who arrived at the same requirements differently and thoroughly researching a particular technology (Db2) so that I could defend it to the rest of the group rather than just voice an opinion. That is similar to how team decisions are actually decided in the workplace, when the researcher must present the argument rather than only possess it. This same discipline was reinforced in a more individual setting by the CS 499 code review process, which involved following a structured checklist and submitting my reasoning for instructor feedback before touching any code. You don't just get to start changing things because you're confident; you have to make the case first.

Communicating with Stakeholders

For me, this became apparent in DAT 210. For a fictional retail company called Running for Glory, a running-specialty store in Seattle that is thinking about expanding, I worked through a complete analytics case. This included situation analysis, data source evaluation, and a final presentation and analysis plan based on SQL, a relational database, and Power BI/Excel visualization. Choosing what to leave out was more difficult than the analysis because the plan had to be directed to a non-technical business partner rather than another analyst. Without hiding behind the ways by which I arrived at my conclusion, I had to interpret what the facts truly supported into language that a store owner could act upon. For the CS 499 code review video, which was intended for peers or a manager rather than a fellow specialist, and for every milestone narrative since, I relied on the same instinct: explain what changed and why it matters before describing how.

Data Structures and Algorithms

Rather than in a single course, this is the area where the curriculum developed the most over time. I had to implement network routing using row reduction, LU decomposition, and Cramer's Rule for MAT 350. I also had to use SVD for a separate image compression project, where I had to consider algorithmic choices in terms of actual trade-offs rather than just accuracy. Building a deep Q-learning agent for a pathfinding problem with experience replay and a target network, as well as doing hyperparameter tests on a CartPole DQN where I had to write an explanation of why one configuration performed better than another, were two examples of how CS 370 advanced reinforcement learning. This comes together most directly in the CS 499 algorithms enhancement: I used a trie-based prefix index for search instead of a linear scan over trip data, and instead of assuming it was faster, I benchmarked it against the previous method and found a 300x speedup at 50,000 trips. The main thing I'm taking from this category is the habit of not just claiming a data structure is better — it's better to demonstrate it.

Software Engineering and Database

The throughline artifact for this entire ePortfolio is my Travlr Getaways program, which was initially developed in CS 465. The database fundamentals that underpin it come from DAD 220 (ER modeling and data modeling using CA ERwin). I revisited the same application in CS 499, focusing on all three enhancement categories: eliminating dead code and centralizing error handling and JWT configuration in the backend; substituting the above trie index for the linear trip search; and improving the database layer itself with actual schema validation, a compound index that truly matches how the app queries data, and an aggregation pipeline that reports average trip length and price by resort. I convinced myself that database work and software engineering aren't actually distinct abilities in practice after completing all three passes on a single codebase rather than three distinct little projects. A query pattern you didn't anticipate appears as a missing index, while a schema decision appears as an API bug three files away. It was more helpful to observe that relationship on a project I was already familiar with than to read about it in a textbook.

Security

When it came to the capstone, security was the outcome for which I had the least amount of evidence, but when I did examine, I discovered the most tangible, solvable issues. The Travlr Getaways backend included a MongoDB connection string that was hardcoded in source rather than being taken from configuration, and a fallback JWT secret that, in the event that the environment variable wasn't specified, would quietly sign authentication tokens with a known string. I had to learn to analyze my own code the same way an outside reviewer would rather than assume it was fine because it ran. Neither of these vulnerabilities is subtle; rather, they're the kind of thing a security-minded reviewer detects right away. I now had a tangible response to the question "how do you think about security in your own code" rather than an abstract one after fixing both and adding true validation to the data layer so invalid input is rejected at the schema level rather than being silently saved.

How the Artifacts Fit Together

Instead of distributing the work over three unconnected projects, I purposefully decided to improve one, Travlr Getaways, across all three categories. The three enhancements that follow this self-assessment — software design and engineering, algorithms and data structures, and databases — are presented in the order that I actually built them, because that order mattered: the software design cleanup came first because the other two categories needed a stable, non-duplicated backend to build on; the trie-based search came second because it is the component that users directly interact with; and the database hardening came last, on purpose, because it touches the schema that the other two categories already rely on. When taken as a whole, they are intended to demonstrate what a hiring manager would want to see in a candidate: not just the ability to develop a feature, but also the ability to examine an existing, functional system, identify its true weaknesses, and make improvements without compromising its functionality.

After this degree, I still want to work in data science, and I'm approaching that goal in the same way that this program pushed me: as the entire pipeline, cleaning and comprehending data, selecting the appropriate technique for the real problem rather than the most showy one, and being able to explain a model's output to someone who isn't technical, not just the modeling step in isolation. Instead of automatically pursuing a master's degree or a certification, I plan to get practical work experience first and let that experience determine whether it is worthwhile. I'm carrying this ePortfolio and the habits that go along with it — benchmarking claims rather than making them, examining my own code like a stranger would, and writing for the reader rather than myself — into that next phase.
