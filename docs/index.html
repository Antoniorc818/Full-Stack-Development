Professional Self-Assessment

Completing the Computer Science program at SNHU, and building this ePortfolio in particular, changed how I think about the work more than any single course did on its own. Coming in, I thought of computer science mostly as writing code that works. What the program pushed me toward, especially in the last year, is thinking about code that works for someone, holds up under real conditions, and can be explained to people who didn't write it. That shift is really the throughline of everything below.

Collaborating in a Team Environment

Most of my coursework has been individual project work, so the clearest example of team collaboration I have is IT 204, where my group was assigned IBM Db2 to research as the DBMS for a database proposal for a fictional client, Birchwood Lane Schools. The work itself was database design, an ER model with entities like Student, Instructor, Course, Enrollment, and Guardian, but the actual skill I practiced was different: reconciling a schema decision with teammates who came at the same requirements differently, and researching a specific technology well enough to defend it to the rest of the group rather than just assert an opinion. The CS 499 code review process reinforced that same discipline in a more individual setting: submitting my reasoning for instructor feedback before touching any code, rather than just acting on confidence.

Communicating with Stakeholders

DAT 210 is where this became concrete for me. I worked through a full analytics case for a fictional retail business, Running for Glory, a Seattle running-specialty store considering expansion, from situation analysis through data source evaluation to a final presentation and analysis plan built around SQL, a relational database, and Power BI/Excel visualization, aimed at a non-technical business partner. The hardest part wasn't the analysis, it was deciding what to leave out and translating what the data actually supported into language a store owner could act on. That's the same instinct behind the CS 499 code review video and every milestone narrative since: describe what changed and why it matters before describing how.

Data Structures and Algorithms

This is the area where the program built up over time rather than in one course. MAT 350 had me implement network routing with row reduction, LU decomposition, and Cramer's Rule, plus an image compression project using SVD. CS 370 pushed further with reinforcement learning: a deep Q-learning pathfinding agent with experience replay and a target network, and CartPole DQN hyperparameter experiments I had to explain in writing. The CS 499 algorithms enhancement is where this came together most directly, replacing a linear scan with a trie-based index and benchmarking the improvement instead of assuming it.

Software Engineering and Database

My Travlr Getaways application, originally built in CS 465, is the throughline artifact for this whole ePortfolio, and DAD 220 is where the database fundamentals underneath it came from. In CS 499 I went back into that same application across all three categories. Doing all three passes on one codebase, instead of three separate projects, is what convinced me that software engineering and database work aren't really separate skills in practice: a schema decision shows up as an API bug three files away, and a query pattern you didn't plan for shows up as a missing index.

Security

Security is the outcome I had the least evidence for going into the capstone, and where I found the most concrete, fixable problems once I actually went looking: a hardcoded fallback JWT secret and a hardcoded database connection string, both the kind of thing a security-minded reviewer catches immediately. Fixing both, and adding real schema-level validation so bad input gets rejected instead of quietly stored, gave me a concrete answer to how I think about security in my own code instead of an abstract one.

How the Artifacts Fit Together

I made a deliberate choice to enhance one artifact, Travlr Getaways, across all three categories instead of spreading the work across three unrelated projects. The three enhancements above are presented in the order I actually built them: software design first, because the other two categories needed a stable, non-duplicated backend to build on; algorithms and data structures second, because it's the piece users directly interact with; and databases last, on purpose, because it touches the schema the other two categories already depend on.

Data science is still where I'm hopefully headed after this degree, and I'm approaching that goal the way this program pushed me to: as the full pipeline, cleaning and understanding data, choosing the right technique for the actual problem, and being able to explain a model's output to someone who isn't technical. I'm planning to get real work experience first and let that tell me whether a master's degree or certification is worth pursuing next. Benchmarking claims instead of asserting them, reviewing my own code like a stranger would, and writing for the reader rather than for myself: that's what I'm bringing into that next step.
