Professional Self-Assessment

This capstone changed how I think about the work more than I expected going in. Coming into CS 499, I thought of the course as a formality at the end of the degree, a chance to tidy up an old project. What it actually became was a full pass through one real codebase, Travlr Getaways, done the way a working developer would do it: review first, plan second, and only then touch the code, with every change backed by a reason I could defend to someone else.

Collaborating in a Team Environment

This capstone is individual work, so the collaboration here took a different shape than a group project: it ran through the code review process itself and through instructor feedback across milestones. Before I changed a single line, I recorded a code review walkthrough of the unenhanced Travlr Getaways codebase, worked through a structured checklist (structure, logic, efficiency, security, testing, documentation), and laid out a plan for someone else, my instructor, to evaluate before I acted on it. Each milestone since then has followed the same pattern: submit, get feedback, incorporate it into the next stage.

Communicating with Stakeholders

Every milestone required a narrative aimed at a reader who wasn't going to just read the diff and infer my reasoning. The code review video was framed for peers or a manager, not a fellow specialist, meaning I had to explain why a hardcoded JWT secret matters without assuming the audience already cared about authentication internals. The written narratives had to justify a technical decision, like replacing a linear scan with a trie, in terms of what it actually changes for the product, not just the algorithm. Writing for that audience repeatedly across four milestones is what sharpened it into a habit.

Data Structures and Algorithms

The algorithms and data structures enhancement is where this outcome came together directly. Trip search in Travlr Getaways only supported an exact match on trip code; anything else meant scanning every record. I built a trie to index trip names and resorts, and rather than assume the complexity argument alone was convincing, I benchmarked it against the old linear scan as trip count scaled up, which showed roughly a 300x improvement at 50,000 trips. That habit, don't claim a data structure is better, prove it, is the biggest thing I'm taking out of this category.

Software Engineering and Database

I made a deliberate choice to enhance one artifact, Travlr Getaways, across all three categories instead of spreading the work across three separate projects. The software design pass removed dead code and centralized error handling in the Express backend; the database pass added real schema validation, a compound index matching how the app actually queries data, and an aggregation pipeline reporting average price and trip length by resort. Doing both passes on the same codebase is what showed me software engineering and database work aren't really separate skills in practice: a schema decision shows up as an API bug three files away, and a query pattern I hadn't planned for shows up as a missing index.

Security

Security is the outcome I had the least evidence for going in, and where the code review process paid off most directly. Reviewing my own code with a security-specific checklist item in mind, rather than just reading it for correctness, is what surfaced a hardcoded fallback JWT secret and a hardcoded MongoDB connection string, both obvious once I was actually looking for them. Fixing both, and adding schema-level validation so bad input gets rejected instead of quietly stored, gave me a concrete answer to how I think about security in my own code.

How the Artifacts Fit Together

The three enhancements above are presented in the order I actually built them: software design first, because the other two categories needed a stable, non-duplicated backend to build on; algorithms and data structures second, because it's the piece users directly interact with; and databases last, on purpose, because it touches the schema the other two categories already depend on. Read together with the code review, they're meant to show that I can look at an existing, working system, find its real weak points, and improve it without breaking what already worked.

This capstone is also where my sense of what data science actually requires sharpened: benchmarking claims instead of asserting them, writing for a reader who wasn't in my head while I coded, reviewing my own work the way an outside reviewer would. Those are the habits I'm bringing into whatever comes next.
