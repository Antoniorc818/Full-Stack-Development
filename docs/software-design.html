Artifact Description

The artifact for this milestone is the backend architecture of Travlr Getaways, a full stack trip-booking application originally built in CS 465, Full Stack Development, using Node.js, Express, and MongoDB with Mongoose on the back end and an Angular admin single-page app on the front end. This enhancement touched the Express API layer under app_api: the routes, the trip and auth controllers, and the JWT authentication configuration.

Justification for Inclusion

The code review turned up structural problems that are common in real codebases. I initially flagged three copies of a travel controller as dead code, but tracing the actual require chain from app.js more carefully showed that was partially wrong:

// app.js requires this chain: app_server/routes/travel.js // requires ↓ → app_server/controllers/travel.js // LIVE — renders the public travel page // genuinely unused, nothing outside them requires either: controllers/travel.js // dead app/app_server/ (entire tree) // dead — duplicate of app_server/ // every trips controller function also repeated this pattern: try { const trip = await Trip.findOne({ code: req.params.tripCode }); res.status(200).json(trip); } catch (err) { res.status(500).json(err); } // and the JWT config had a hardcoded fallback const secret = process.env.JWT_SECRET || 'MY_SUPER_SECRET_KEY';

Catching that first-pass mistake, and re-verifying it against the actual import graph instead of trusting my own initial read, ended up being as much a part of this enhancement as the fix itself. I removed only the two files that were actually dead, left app_server/controllers/travel.js in place since it's genuinely in use, extracted the repeated try/catch pattern into centralized error-handling middleware, and removed the hardcoded JWT fallback in favor of startup validation that fails loudly if JWT_SECRET isn't set.

Together these show my ability to identify structural debt in an existing codebase and verify that identification against the code itself, design centralized, reusable logic instead of duplicating it, and apply secure configuration practices instead of hardcoding secrets.

Course Outcomes

This enhancement maps to Course Outcome 4, using well-founded tools and techniques to make an existing solution more maintainable, and Course Outcome 5, developing a security mindset by removing a hardcoded credential and replacing it with fail-fast validation.

Reflection

The dead code removal taught me something the code review process itself was supposed to catch: I flagged all three travel.js copies as dead without tracing the require chain all the way through, and only caught that one was live when I went back to actually remove them. That's a real lesson in defensive reading of a codebase, don't delete or claim to have deleted something just because it looks unused, trace the actual import graph first. A wrong assumption at the review step would have carried straight through into a broken app if I'd deleted all three.

The error-handling middleware took more thought than expected: I didn't want to leak internal error details to the client, but I also didn't want every failure to collapse into one unhelpful message, so I settled on distinguishing validation errors (422, field-level messages), duplicate-key errors (409), and everything else (a generic 500, no internals leaked).

This enhancement set up the other two categories more than I expected. The centralized error handling made it easier to add the search endpoint in the algorithms milestone without repeating the pattern I'd just removed, and the JWT_SECRET environment-variable pattern is exactly what I reused later for the MongoDB connection string in the databases milestone.
