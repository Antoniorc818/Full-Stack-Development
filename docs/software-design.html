Artifact Description

The artifact for this milestone is the backend architecture of Travlr Getaways, a full stack trip-booking application originally built in CS 465, Full Stack Development, using Node.js, Express, and MongoDB with Mongoose on the back end and an Angular admin single-page app on the front end. This enhancement touched the Express API layer under app_api: the routes, the trip and auth controllers, and the JWT authentication configuration.

Justification for Inclusion

The code review turned up structural problems that are common in real codebases. I initially flagged three copies of a travel controller as dead code, but tracing the actual require chain from app.js more carefully showed that was partially wrong:

// app.js requires this chain: app_server/routes/travel.js // requires ↓ → app_server/controllers/travel.js // LIVE — renders the public travel page // genuinely unused, nothing outside them requires either: controllers/travel.js // dead app/app_server/ (entire tree) // dead — duplicate of app_server/ // JWT config was duplicated in two places, each with its own fallback secret // every controller function repeated its own try/catch, inconsistently // no real input validation beyond a manual null check

Catching that first-pass dead-code mistake, and re-verifying it against the actual import graph instead of trusting my own initial read, ended up being as much a part of this enhancement as the fix itself. I removed only the two files that were actually dead, left app_server/controllers/travel.js in place since it's genuinely in use, pulled JWT configuration into a single module (app_api/config/auth.js) that throws on startup if the secret isn't set, added centralized error-handling middleware with an asyncHandler wrapper, and added an express-validator layer that checks registration, login, and trip data before it reaches a controller.

Testing & a Real Bug

Getting the server to boot cleanly wasn't enough to prove the enhancement worked, so I exercised the real endpoints. Registering a user with a short password correctly returned a 422 with a specific field message. But testing the public trip-listing endpoint turned up a genuine bug: a GET to /api/trips returned "No authorization token was found" despite the route being intentionally public. Tracing it down, app_api/routes/index.js already applied auth correctly, only to the create/update/delete routes — but app.js separately applied a blanket JWT check to everything under /api except login/register, and the app-level check was overriding the more precise route-level design. Since the per-route auth was already the accurate source of truth, I removed the blanket check from app.js entirely.

Testing also surfaced a second issue I deliberately did not fix here: the Trip schema defines a perPerson field, but the actual seed data uses price. My new validator checks for perPerson, so this wouldn't break reading existing trips, but it would break creating or updating one. That predates this enhancement and is a data-model issue rather than a software design one, so I documented it as a known limitation instead of scope-creeping into fixing it here.

Course Outcomes

The refactor into config, middleware, and validator modules is a direct application of separation of concerns, and it held up under real endpoint testing, not just a syntax check — this speaks to Course Outcome 4. It also touches Course Outcome 5: removing the hardcoded fallback secret, keeping raw database errors away from API callers, and catching the overlapping auth logic are real steps toward a security mindset. That said, the security work isn't fully finished — the price/perPerson mismatch and things like rate limiting are still open, so I'd call this outcome partially rather than fully met.

Reflection

The biggest lesson was how much a clean server boot can hide: every file loaded, there were no syntax errors, no startup crash — and there was still a real bug in the auth logic that only showed up once I actually called the endpoints. The auth bug was a good example of why centralizing logic matters: it existed because two files had different opinions about which routes needed tokens, and nothing forced those opinions to agree.

I also had to draw a line on scope. Fixing the price/perPerson mismatch would have been easy once I found it, but it's a different problem than this milestone is about, so documenting it honestly felt more appropriate than quietly fixing it or quietly ignoring it. And the dead-code lesson from the code review still applies: don't delete, or claim to have deleted, something just because it looks unused — trace the actual import graph first.

This enhancement set up the other two categories more than I expected. The centralized error handling made it easier to add the search endpoint in the algorithms milestone without repeating the pattern I'd just removed, and the JWT_SECRET environment-variable pattern is exactly what I reused later for the MongoDB connection string in the databases milestone.
