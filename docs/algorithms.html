Artifact Description

The artifact for this milestone is the trip search functionality of Travlr Getaways. Before this enhancement, the only way to retrieve a specific trip through the API was an exact match on its trip code, using Trip.findOne against the code field — no way to search by name or resort, no partial matching, no autocomplete.

Justification for Inclusion

The missing capability wasn't a bug so much as a scaling problem waiting to happen. Without an index, the only option to add name/resort search would have been a linear scan across every trip document — fine at a handful of trips, but it gets slower in direct proportion to how many trips exist, which matters a lot for something like autocomplete running a new search on every keystroke.

To fix that, I built a trie — a prefix tree — that indexes trip names and resorts (app_api/utils/trie.js and tripIndex.js). A trie stores strings letter by letter down a tree structure, so a prefix search means walking one path in the tree instead of scanning every record.

// prefix lookup: O(k) for a query of length k // instead of O(n) linear scan across n trips tripIndex.search('par') // -> ['Paris Getaway', 'Paris Romance Weekend', ...]

I wrote a standalone benchmark script (scripts/benchmark-search.js) that generates synthetic trip data at increasing scale and times the trie against the linear scan it replaced, rather than just asserting it would be faster:

Trips indexed Linear scan (avg ms/query) Trie search (avg ms/query) Speedup
1000.21600.002489.3x
1,0000.32410.004277.6x
10,0001.60070.0036446.8x
50,0005.31720.0169314.2x

The trade-off I anticipated in the Module One enhancement plan is a small amount of extra memory to hold the index in exchange for search time that depends on the length of the query rather than the size of the catalog — the trie stays relatively flat as trip count grows while the linear scan steadily slows down.

The index is built on the backend at startup and exposed through a new /api/trips/search endpoint, used by a debounced search box I wired into the Angular admin trips component, updated incrementally whenever a trip is added, modified, or deleted rather than rebuilt from scratch on each request.

Course Outcomes

This enhancement aligns with Course Outcome 3, using algorithmic principles to design and evaluate a solution while managing the trade-off between memory usage (the trie's index) and lookup speed, and Course Outcome 4, using a well-founded technique to deliver a measurable improvement, integrated end to end from the backend index through the API route to a working search box in the admin UI.

One update to the original plan: I hadn't initially specified how the index stays accurate once trips are added, renamed, or removed after the server starts — the Module One pseudocode focused mainly on building and benchmarking the trie. In practice, before an update finishes I fetch the trip's previous state so the old name/resort can be removed from the index before the new values go in, and a delete fully removes its entries. That's a small extension of the original scope, but it's still an algorithmic design decision about maintaining the data structure, not a separate feature.

Reflection

I went in assuming the trie would be faster and treated the benchmark as a formality — but actually running it and watching the gap widen as trip count scaled up made the improvement concrete in a way the Big-O argument alone hadn't. That's a habit I want to keep: measure the claim, don't just derive it.

Two things stood out while building this. First, route ordering: Express matches routes in registration order, so GET /trips/search has to be declared before the existing GET /trips/:tripCode, or every search request gets swallowed as if "search" were a trip code. I caught this before it shipped, but it was a good reminder that adding an endpoint to an existing REST API takes more than writing the handler.

Second, a test that initially looked like a bug in my own remove logic: renaming a trip seemed to leave the old name searchable. The project's asyncHandler wrapper (from Milestone Two) doesn't return the promise from the controller function, which is correct for how Express calls route handlers, but it meant my test moved on before the controller had actually finished. After isolating the trie by itself and confirming it removed entries correctly, I traced the real issue to the test harness and changed it to wait for a signal from res.json() instead of the controller call directly. A failing test doesn't always mean the code under test is wrong.

The trie also keeps nodes in memory permanently even after every trip using them is removed, which is a reasonable trade-off for an admin tool with a modest number of trips, but would need trimming logic under much higher churn. I documented that limitation directly in the code rather than leaving it silent — not every inefficiency needs fixing right away, but it does need to be named.

While testing end-to-end locally (search, add, edit, delete against the real Angular admin UI, not just scripted tests), I also found and fixed two pre-existing bugs unrelated to search itself: authentication.service.ts was using relative URLs instead of the backend's absolute URL, and the trip-edit and trip-card components were sending MongoDB's internal _id instead of the trip's code field to routes keyed on code, causing edits and deletes to fail with 404s. Neither was caused by this enhancement, but both surfaced while exercising the app to verify the index-syncing logic under real conditions, and leaving them in place would have undermined that verification — renaming a trip through the UI now correctly removes it from search under the old name and makes it findable under the new one.
